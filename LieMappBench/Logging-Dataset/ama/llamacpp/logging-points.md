# AMA · llama.cpp 로깅 지점

## 무엇을 확인하는가

AMA는 도구의 이름·설명·매개변수 스키마를 매력적으로 작성하여 LLM Agent가 공격자 도구를 선택하도록 유도하는 공격이다. 이 실험은 **도구 메타데이터 입력 → 실제 모델 입력 → 모델의 도구 선택 → 에이전트의 실행**을 요청 단위로 연결한다.

조건의 원본은 `attack_library.xlsx`의 `AI 포렌식` 시트 G11(AC1~AC3), H11(DC1~DC2)이다. AC3의 T는 **보안 검토 수행**, DC의 T는 **기록 가능**이라는 의미이다. 모든 AC가 T이면 공격이 성립한다는 방식으로 해석하지 않는다.

**LP01을 택한 이유:** 에이전트가 전송했다고 주장한 자료와 엔진이 실제 수신한 자료를 구분하기 위해서다. 도구 설명은 생략·요약하지 않고 그대로 저장한다.

**LP02를 택한 이유:** 수신한 도구 설명이 템플릿 처리를 거쳐 실제 모델 입력에 반영되는지를 확인하기 위해서다. 이 지점의 구조 검증이나 템플릿 적용을 메타데이터 보안 검사로 간주하지 않는다.

**LP03을 택한 이유:** 모델이 반환한 함수명과 인자를 후보 메타데이터 및 실행 기록과 연결하기 위해서다. 이 지점은 실제 native llama.cpp 추론 경로이며, 모델 응답을 사람이 대신 작성하지 않는다.

| DC1 · 선택 도구 메타데이터 기록 | 선택 함수명을 유일한 도구 정의에 연결한 정확한 메타데이터 | 도구 후보 전체 기록과 최종 선택 도구 기록은 구분 필요 |

`LP03.raw.tool_dispatch_observed=false`는 **이 엔진 지점에서 실제 도구 실행을 관측하지 않는다**는 뜻이다. 에이전트 전체에서 호출이 없었다는 뜻이 아니다.

## 활성화와 연결 방식

1. 공통 `logger.py`의 `Collector`를 시작하고 서버 프로세스에 `LIEMAPP_SOCKET`을 전달한다.
2. `/v1/chat/completions` 요청에 유일한 문자열 `liemapp_request_id`를 넣는다. `liemapp_context` 객체에는 실험군·대조군 등 실험 라벨을 넣을 수 있다.
3. 세 지점은 같은 `context.request_id`와 `raw.request_id`를 기록한다. 원시값·소스 경로·행 번호·소스 해시·이벤트 해시는 공통 Logger가 저장한다.

실험 범위는 `stream=false`, `n=1`이다. 자동 선택 실험은 `tool_choice=auto`로 수행한다. 고정 도구 대조군은 후보를 지정된 정상 도구 한 개로 제한하고 `tool_choice=required`를 사용한다. 두 경우의 의미를 혼동하지 않는다.

`LIEMAPP_SOCKET`이 없으면 native 로깅은 비활성화된다. 요청별 문맥은 함수 인자로 전달하며, 서버 프로세스의 환경변수를 요청마다 변경하지 않는다. 따라서 병렬 요청의 식별자가 서로 섞이지 않는다.

## 해석의 경계

- 이 문서는 소스 분석과 로깅 지점의 근거이다. 공격 성공 여부는 실제 실행의 봉인된 로그와 Analyzer 보고서로 확인한다.
- 원본 엔진 `LIE/llama.cpp`는 수정하지 않고, AMA용 별도 계측본만 사용한다.
- native 엔진 소스에서 확인한 내용과 연구용 에이전트에서 확인한 내용을 분리한다. 에이전트의 출처·정책을 엔진 고유 기능으로 설명하지 않는다.
- 로그에는 합성 실험 데이터만 넣는다. 프롬프트와 인자 전체가 저장되므로 실제 개인정보·API 키를 넣어서는 안 된다.
